## 1. 設計判断

### 1a. 値/命令の表現 = arena + enum (最重要)
go/ssa の `Value`/`Instruction`/`Member`/`Node` の4インタフェースと55の具象型を、guff-types と同じ **arena + enum + ID index** で表す。`Box<dyn Value>` / `Rc<RefCell>` は使わない(プロジェクト方針・SSAはtype-switch多用でenum向き)。

- SSA全体を関数横断で保持する `Program` が複数 arena を所有。ID型(`NonZeroU32`, 1-indexed):
  - `FuncId` / `BlockId` / `ValueId` / `InstrId` / `PackageId(ssa)`。
- `ValueData` enum … `Alloc`/`BinOp`/`Builtin`/`Call`/`Const`/`Convert`/`Extract`/`Field`/`FieldAddr`/`FreeVar`/`Global`/`Index`/`IndexAddr`/`Lookup`/`MakeChan`/`MakeClosure`/`MakeInterface`/`MakeMap`/`MakeSlice`/`MultiConvert`/`Next`/`Parameter`/`Phi`/`Range`/`Select`/`Slice`/`SliceToArrayPointer`/`TypeAssert`/`UnOp`/`ChangeType`/`ChangeInterface` …
- `InstrData` enum … 値を兼ねるもの(上記の多く) + `DebugRef`/`Defer`/`Go`/`If`/`Jump`/`MapUpdate`/`Panic`/`Return`/`RunDefers`/`Send`/`Store`。
- **値かつ命令**の型(`BinOp`等)は「命令 arena に置き、`ValueId` はその命令を指す」形にする(go/ssa と同じく1オブジェクトが両インタフェースを満たす)。具体的には `Value` を `enum { Ref(InstrId), Const(..), Param(..), FreeVar(..), Global(FuncOrGlobalId), Builtin(..), Function(FuncId) }` のような薄いハンドルにし、命令が結果値を兼ねるものは `Ref(InstrId)` で参照する案を第1候補とする(chunk 2 で最終確定)。

### 1b. 型情報との結合 = 読み取り借用
- SSA は `TypeId`/`ObjectId` を持ち回るだけで型を再定義しない。`Program` は checker が持つ型 arena 群(`TypeArena`/`ObjectArena`/`ScopeArena`/`PackageArena`)への参照(または移譲された所有)を保持する。
- go/ssa が呼ぶ型ユーティリティ(`types.Identical`/`Unalias`/`NewPointer`/`NewTuple`/`NewSignatureType`/`Instantiate`/`Selection`/`Typ[...]`)は guff-types に既存。無い薄いラッパは `guff-types` 側に足すのではなく ssa crate 内 util に置く。
- **借用モデルの確定は chunk 1 の設計課題**。第1候補: SSA構築APIは `&Checker`(または checker から取り出した arena 束)を受け取り、SSA arena だけを `&mut` で構築する。型 arena を SSA 構築中に変更する必要があるのは generics 実体化(`Instantiate`)だけ → そこは後続マイルストーン。naive SSA では型 arena は read-only で済む見込み。

### 1c. 移植する内部小物
- `typeutil.MethodSetCache` → `TypeId → メソッドセット` のメモ化。guff-types の `lookup`/`typeset` を土台に薄く。
- `internal/typeparams.Free` → 「型が型パラメータを参照するか」のメモ化(`hasParams`)。
- `canonizer`(`types.Context` ベースの型正準化) → generics マイルストーンまで defer。naive SSA では identity ベースで代用。

## 3. テスト戦略

### 3a. モジュール単体テスト (各チャンク)
- 各チャンクで `crates/guff-ssa/tests/*.rs` に `#[test]` を追加。guff-types と同じく **チャンク毎に総テスト件数を記録**。
- 対象: arena 操作、`BuilderMode` フラグ、const 生成、CFG 構築(ブロック接続/succ/pred)、emit ヘルパ、dom アルゴリズム 等の局所ロジック。

### 3b. golden 逆アセンブル比較 (回帰網の主軸)
SSA構造の正しさを一括検証する。手順:
1. `tests/golden/*.go` に小さな Go プログラムを置く。
2. **期待値生成ハーネス**(Goワンショット): `/Users/dakimura/sdk/go1.26.4/bin/go` で小さな Go ドライバ(`golang.org/x/tools/go/ssa` + `ssautil` を使い `Function.String()` / package 逆アセンブルを出力)を実行し、`tests/golden/*.ssa.expected` を生成。ビルドモードは `NaiveForm`(lift無し)で固定し、最初のマイルストーンと揃える。
   - このドライバは `projects/` 配下にコミットして再生成可能にする(初回は手動生成 → CIでは既存expected固定)。
3. Rust側テストが同じ .go を guff(scanner→parser→types→ssa)に通し、`print.rs` の逆アセンブル文字列を expected と比較。
4. 差分が出たら unified diff を表示。**位置情報(pos)由来の差はマスク**(guff-types の pos は byte offset ベースで go/token と表示が異なるため、golden比較では pos 列を正規化 or 無視)。

> 注: golden は「NaiveForm + 決定的な値/ブロック番号付け」を前提にする。go/ssa の値番号(`t0`,`t1`,…)とブロック番号の採番順を忠実に移植することが golden 一致の鍵 → builder/emit の採番順を go/ssa と1対1に保つ。

### 3c. (将来) interp 実行検証
`ssa/interp` を別クレートで移植し、golden プログラムを実行して結果照合。強力だが大規模 → 当面対象外。マイルストーン F 以降の候補。
